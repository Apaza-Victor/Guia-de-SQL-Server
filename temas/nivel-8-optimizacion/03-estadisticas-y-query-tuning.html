Estadísticas y Query Tuning

Las estadísticas contienen información sobre la distribución de datos en columnas y son esenciales para que el optimizador estime cardinalidades (número de filas) y elija el plan más eficiente. Sin estadísticas actualizadas, el optimizador trabaja a ciegas.

¿Qué son las Estadísticas?

SQL Server mantiene histogramas y densidades de las columnas indexadas y, opcionalmente, de columnas no indexadas. El histograma divide los datos en hasta 200 rangos (steps) y cuenta la frecuencia.

T-SQL
-- Ver estadísticas de una tabla
DBCC SHOW_STATISTICS('clientes', 'idx_clientes_ciudad');

-- Actualizar estadísticas
UPDATE STATISTICS clientes;
UPDATE STATISTICS clientes idx_clientes_ciudad;
UPDATE STATISTICS clientes WITH FULLSCAN;     -- Escaneo completo
UPDATE STATISTICS clientes WITH SAMPLE 10 PERCENT;  -- Muestreo

Auto-Update de Estadísticas

SQL Server actualiza estadísticas automáticamente cuando cambian suficientes filas. El umbral es:

  • Tablas de >500 filas: cada 500 + (20% de filas) modificaciones.
  • Tablas temporales y variables de tabla pueden no tener estadísticas actualizadas.

Se puede controlar con AUTO_UPDATE_STATISTICS a nivel de base de datos.

Estimación de Cardinalidad (CE)

El optimizador usa la cardinalidad estimada para elegir operadores (Nested Loops, Hash Match, Merge Join). Una mala estimación lleva a malos planes. SQL Server 2014+ introdujo el CE de nueva generación (Cardinality Estimation 130+ y 140+).

T-SQL
-- Ver nivel de CE de la BD
SELECT name, compatibility_level FROM sys.databases;

-- Forzar CE legacy (para compatibilidad)
ALTER DATABASE MiBD SET COMPATIBILITY_LEVEL = 120;
-- Usar CE de SQL Server 2017 (140)
ALTER DATABASE MiBD SET COMPATIBILITY_LEVEL = 140;

Parameter Sniffing

SQL Server genera un plan de ejecución basado en los valores de los parámetros en la primera ejecución ("sniffing"). Ese plan se reutiliza, pero puede ser subóptimo para otros valores.

T-SQL
-- Síntoma: SP funciona rápido para unos valores y lento para otros
CREATE PROCEDURE uspBuscarPedidos
    @FechaInicio DATE
AS
    SELECT * FROM pedidos WHERE fecha >= @FechaInicio;

-- Soluciones:
-- 1. WITH RECOMPILE (nuevo plan cada vez)
CREATE PROCEDURE uspBuscarPedidos
    @FechaInicio DATE
WITH RECOMPILE
AS ...

-- 2. OPTIMIZE FOR UNKNOWN (usa promedio)
SELECT * FROM pedidos
WHERE fecha >= @FechaInicio
OPTION (OPTIMIZE FOR (@FechaInicio UNKNOWN));

-- 3. OPTION (RECOMPILE) solo en la consulta
SELECT * FROM pedidos
WHERE fecha >= @FechaInicio
OPTION (RECOMPILE);
Parameter sniffing

El parameter sniffing no es un bug; es una característica de optimización. El problema surge cuando los datos están desbalanceados. Las soluciones incluyen WITH RECOMPILE, OPTIMIZE FOR UNKNOWN, o dividir el SP con lógica condicional para diferentes rangos de valores.

DMVs Útiles para Query Tuning

DMVPropósito
sys.dm_db_missing_index_detailsÍndices sugeridos por el optimizador
sys.dm_db_missing_index_columnsColumnas específicas para el índice faltante
sys.dm_exec_query_statsEstadísticas de consultas (CPU, lecturas, duración)
sys.dm_exec_query_planPlan de ejecución XML
sys.dm_db_index_usage_statsUso de índices (lecturas vs escrituras)
sys.dm_exec_sql_textTexto SQL de un plan o solicitud
sys.dm_exec_requestsConsultas activas en el servidor
sys.dm_os_wait_statsEstadísticas de esperas (cuellos de botella)
T-SQL
-- Índices faltantes (missing indexes)
SELECT
    migs.avg_total_user_cost * migs.avg_user_impact / 100 AS improvement,
    mid.statement AS tabla,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns,
    migs.unique_compiles
FROM sys.dm_db_missing_index_groups mig
JOIN sys.dm_db_missing_index_group_stats migs
    ON migs.group_handle = mig.index_group_handle
JOIN sys.dm_db_missing_index_details mid
    ON mig.index_handle = mid.index_handle
WHERE mid.database_id = DB_ID()
ORDER BY improvement DESC;
