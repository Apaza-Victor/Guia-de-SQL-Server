Buenas Prácticas de Rendimiento

Este tema sintetiza las técnicas más efectivas para escribir consultas eficientes en SQL Server. Aplicar estas prácticas marca la diferencia entre un sistema responsivo y uno lento.

1. SARGability

Una expresión es SARGable (Search ARGument) cuando el optimizador puede usar un índice seek. Evita envolver columnas en funciones.

T-SQL
-- ❌ No SARGable
SELECT * FROM pedidos WHERE YEAR(fecha) = 2024;
SELECT * FROM clientes WHERE UPPER(nombre) = 'JUAN';
SELECT * FROM ventas WHERE fecha + 1 = GETDATE();

-- ✅ SARGable
SELECT * FROM pedidos WHERE fecha >= '2024-01-01' AND fecha < '2025-01-01';
SELECT * FROM clientes WHERE nombre = 'Juan';
SELECT * FROM ventas WHERE fecha = DATEADD(DAY, -1, CAST(GETDATE() AS DATE));

2. Evitar SELECT *

T-SQL
-- ❌ SELECT *: trae columnas innecesarias, impide covering indexes
SELECT * FROM clientes WHERE ciudad = 'Bogotá';

-- ✅ Solo las columnas necesarias
SELECT id_cliente, nombre, email FROM clientes WHERE ciudad = 'Bogotá';

3. EXISTS vs IN

T-SQL
-- ❌ IN con subconsulta (puede ser ineficiente)
SELECT * FROM clientes WHERE id_cliente IN (
    SELECT id_cliente FROM pedidos WHERE total > 1000
);

-- ✅ EXISTS (corta al encontrar la primera coincidencia)
SELECT c.* FROM clientes c
WHERE EXISTS (
    SELECT 1 FROM pedidos p
    WHERE p.id_cliente = c.id_cliente AND p.total > 1000
);

4. NOT EXISTS vs NOT IN

T-SQL
-- ❌ NOT IN puede dar resultados inesperados con NULLs
SELECT * FROM clientes WHERE id_cliente NOT IN (
    SELECT id_cliente FROM pedidos
);

-- ✅ NOT EXISTS maneja NULLs correctamente
SELECT * FROM clientes c
WHERE NOT EXISTS (
    SELECT 1 FROM pedidos p
    WHERE p.id_cliente = c.id_cliente
);

5. Tipos de Datos Apropiados

T-SQL
-- ❌ Tipos incorrectos
CREATE TABLE usuarios (
    activo VARCHAR(1),       -- Debería ser BIT
    fecha_nacimiento DATETIME,  -- Solo fecha: usar DATE
    salario FLOAT,              -- Dinero: usar DECIMAL(18,2) o MONEY
    codigo_postal INT           -- Códigos con ceros a la izquierda: VARCHAR(10)
);

-- ✅ Tipos adecuados
CREATE TABLE usuarios (
    activo BIT,
    fecha_nacimiento DATE,
    salario DECIMAL(18,2),
    codigo_postal VARCHAR(10)
);

6. Evitar Cursores

T-SQL
-- ❌ Cursor innecesario
DECLARE c CURSOR FOR SELECT id_producto, precio FROM productos;
OPEN c; FETCH NEXT FROM c INTO @id, @precio;
WHILE @@FETCH_STATUS = 0
BEGIN
    UPDATE productos SET precio = @precio * 1.1 WHERE id_producto = @id;
    FETCH NEXT FROM c INTO @id, @precio;
END;
CLOSE c; DEALLOCATE c;

-- ✅ Set-based
UPDATE productos SET precio = precio * 1.1;

7. Evitar Funciones en WHERE

T-SQL
-- ❌ Función en columna indexada
SELECT * FROM pedidos WHERE DATEPART(month, fecha) = 12;

-- ✅ Rango
SELECT * FROM pedidos WHERE fecha >= '2024-12-01' AND fecha < '2025-01-01';

8. Transacciones Cortas

T-SQL
-- ❌ Transacción larga con lógica innecesaria
BEGIN TRAN;
    DECLARE @total DECIMAL = 0;
    SELECT @total = SUM(total) FROM pedidos WHERE fecha >= '2024-01-01';
    -- ... lógica de aplicación ...
    UPDATE clientes SET saldo = @total WHERE id = 1;
COMMIT;

-- ✅ Transacción mínima
BEGIN TRAN;
    UPDATE clientes SET saldo = (SELECT SUM(total) FROM pedidos WHERE fecha >= '2024-01-01')
    WHERE id = 1;
COMMIT;
Query Store

El Query Store (disponible desde SQL Server 2016) actúa como una "caja negra" que registra el rendimiento histórico de las consultas. Permite identificar regresiones, forzar planes de ejecución y analizar tendencias. Habilítalo con ALTER DATABASE MiBD SET QUERY_STORE = ON;. Es la herramienta más útil para diagnóstico de rendimiento en producción.
